# Weekly Case Report

你是一個「Case 討論與書面報告」工作流，不是摘要器。

## 目標

讀取專案根目錄 `input/` 內本週的兩份 Case 資料，生成一份可直接繳交的繁體中文 PDF。
每次輸入固定為兩個 Case 檔案，各自獨立分析，合併在同一份報告中。

教師期待的不只是內容摘要，而是（對每個 Case 都要做到）：

1. 準確掌握 Case 的背景、利害關係人、事件與核心問題。
2. 找出真正值得討論的矛盾、取捨與不確定性。
3. 呈現多元觀點，而不是只給單一答案。
4. 展現觀點碰撞、反駁、修正與整合的過程。
5. 從 Case 延伸到更一般化的管理、組織、倫理、策略或決策議題。
6. 最後形成一個有條件、有邏輯的本組綜合觀點。
7. 輸出排版完成的 `output/case_report.pdf`。

## 啟動時不要先問問題

除非 `input/` 完全沒有可讀資料，否則直接開始。
如果缺少非必要資訊（課程名稱、組員姓名等），使用中性標示或省略，不阻塞流程。

## Step 1 — 掃描輸入資料與辨識兩個 Case

先列出 `input/` 內所有檔案。預期有兩個 Case 檔案（可能是 2 個 PDF、1 PDF + 1 DOCX 等任意組合）。

支援優先順序：
- PDF
- DOCX
- PPTX
- TXT / MD
- CSV / XLSX（若對 Case 有意義）
- 圖片

執行：

```bash
python .claude/skills/case-report/scripts/extract_sources.py input work/source_text.md
```

若腳本無法處理某個檔案，直接用 Claude Code 能力讀取該檔，不要因單一檔案失敗而停止。

讀完 `work/source_text.md` 後：
1. 辨識哪些內容屬於 Case 1、哪些屬於 Case 2（通常每個檔案就是一個 Case）。
2. 按檔名或內容中的標題，為每個 Case 取一個簡短代稱（如 Case 原名）。
3. 必要時回到原始檔確認表格、圖、附錄或語境。

若 `input/` 內只有一個 Case 檔案，正常以單 Case 模式執行（報告結構省略 Case 分隔，回退到單 Case 版面）。若超過兩個 Case 相關檔案，先根據檔名與內容判斷哪些檔案屬於同一個 Case。

## Step 2 — 建立 Case Map（每個 Case 各一份）

對 Case 1 與 Case 2 各自在內部整理以下項目，但不要直接把這份 checklist 原樣塞進報告：

- 背景與時間線
- 關鍵人物 / 部門 / 組織
- 各方目標與誘因
- 已知事實
- 不確定資訊
- 顯性問題
- 隱性問題
- 權力關係
- 資源限制
- 短期與長期後果
- 可行選項

任何重要事實都必須能回溯到輸入資料。
不可為了讓報告更完整而虛構 Case 中不存在的數字、對話、事件或人物動機。

## Step 3 — 找出「值得辯證」的核心爭點（每個 Case 各自）

對每個 Case 各自至少選 3 個、最多 5 個真正有張力的爭點。

好的爭點通常長這樣：

- 效率 vs 公平
- 部門自主 vs 組織整合
- 短期績效 vs 長期能力
- 權責明確 vs 彈性協作
- 個人責任 vs 制度設計
- 競爭式處理 vs 合作式處理
- CEO / 高層介入 vs 基層自行協調
- 程序正義 vs 結果最佳化

不要硬套上述類型；以 Case 本身為準。

每個爭點至少回答：

- 為什麼會產生？
- 兩邊各自合理的地方是什麼？
- 各自忽略了什麼？
- 在什麼條件下其中一邊會更合理？
- 有沒有第三種方案？

## Step 4 — 多元觀點與組內辯證（每個 Case 各自）

先檢查 `input/` 是否含有：

- `group_notes`
- `discussion`
- `meeting`
- `chat`
- `討論`
- `組員`
- `課堂筆記`
- 或任何明顯屬於組員觀點的資料。

### 若有真實組員討論資料

忠實整理不同觀點，不必硬湊每個人都不同。
可以寫：

- 初始觀點
- 反方疑慮
- 互相挑戰
- 修正後觀點
- 尚未完全解決的分歧

### 若沒有真實組員討論資料

**禁止**捏造「A 組員認為」「某位組員提出」。

改用「觀點 A / 觀點 B / 觀點 C」作為分析角色，模擬合理的辯證，再用：

- 「從本組可採取的分析角度來看」
- 「若進一步討論，可形成以下兩種立場」
- 「綜合上述不同觀點」

等中性寫法。

報告最重要的不是演戲，而是讓讀者看見：
**「為什麼一開始會有不同答案，以及經過什麼推理後才得到較成熟的看法。」**

## Step 5 — 延伸思考（每個 Case 各自）

對每個 Case 各自至少加入 2 個 Case 之外、但與該 Case 高度相關的延伸。

延伸方式可包含：

- 把 Case 放進理論框架
- 換一個利害關係人的視角重做判斷
- 改變一個前提後做反事實分析
- 討論制度設計，而不是只處理當下事件
- 對照其他產業或組織情境
- 找出「這個方法什麼時候會失效」
- 探討倫理、治理、權力、激勵、資訊不對稱等更深層問題

延伸必須服務於 Case，不要寫成離題的小論文。

若需要外部資料：

- 只有在能提升分析品質時才搜尋。
- 外部事實要附來源。
- 不要讓外部資料蓋過 Case 本身。

## Step 6 — 形成綜合觀點（每個 Case 各自）

對每個 Case 各自形成綜合觀點。避免寫成「所以方案 X 一定最好」。

好的結論應包含：

- 本組目前較支持的方向
- 支持它的核心理由
- 它成立所需的條件
- 可能的風險
- 若條件改變，何時應改採其他方案

結論應該看得出前面辯證真的改變或精煉了判斷。

## Step 7 — 撰寫正式報告

讀取：

- `references/report_structure.md`
- `references/quality_rubric.md`
- `assets/report_template.md`

生成 `output/case_report.md`。

報告結構：以 Case 為單位分為兩大部分，各自包含完整的分析段落（背景、利害關係人、爭點、辯證、延伸、綜合觀點）。共用封面與結語。詳見 `references/report_structure.md`。

寫作原則：

- 繁體中文。
- 大學生正式報告語氣，但不要像 AI 教科書。
- 多用完整段落，少用碎片化 bullet。
- 每個 Case 的摘要只占該 Case 篇幅約 20–30%；分析、辯證、延伸至少 70%。
- 不要每段都用「此外、再者、綜上所述」。
- 不要重複 Case 原文。
- 對不確定資訊清楚標示。
- 不虛構組員觀點。
- 每個 Case 預設 2500–4000 中文字（全文約 5000–8000 字）；Case 特別複雜可更長。
- 標題清楚，但避免層級過度細碎。
- 兩個 Case 各自獨立，不需要刻意比較或找共通點。

### 語感與去 AI 腔

以下是常見的 AI 生成痕跡，必須刻意避開：

- **禁止濫用「不是 A，而是 B」句型。** 偶爾用一次可以，但不要變成段落的預設節奏。改用直述：直接說你要說的，不需要先否定一個稻草人再轉折。
- **中文詞不要每個都括號附英文。** 只在以下情況附原文：該英文詞是 Case 原文的關鍵術語且中文翻譯不唯一（如 agency 可譯為能動性或代理權），或該詞首次出現且讀者可能需要回查原文。一般常見詞彙（judgment、voice、presence、efficiency）不需要附。整份報告附英文的地方不應超過 5–8 處。
- **少用冒號開頭的展開句。** 「原因是：……」「具體而言：……」「風險在於：……」這類句法偶爾出現沒問題，但如果每段都靠冒號把後半句掛上去，讀起來會像在填表格。改用正常的主詞動詞結構把意思寫完。
- **避免機械式的平行排列。** 不要每個爭點都用完全相同的子結構（「支持 X 的一方……但這忽略了……反方則……」）。真人寫報告時，不同爭點的展開方式本來就不一樣——有的先舉例再歸納，有的先給結論再拆解條件，有的用反問帶出。
- **不要把每個段落都寫成辯論稿。** 不是每句話都需要「然而」「但」「不過」來轉折。有些判斷可以直接給，不必先鋪一個對立面再翻過來。
- **少用名詞化堆疊。** 「進行判斷的動作」→「判斷」；「具有收斂效果的中介系統」→ 簡化成更口語但仍正式的說法。中文不像英文那樣習慣長名詞片語，堆太多會顯得翻譯腔。
- **禁止濫用「橫跨」「交織」等宏觀空泛動詞。** 「橫跨不同層級」「高度交織」這類用法是 LLM 處理管理類文章的高頻口頭禪，人類寫作中極少這樣密集使用。遇到想寫「橫跨」的地方，改用具體描述（「從基層員工到高階主管都牽涉其中」比「橫跨不同層級」真實得多）。
- **打破「觀點 A……觀點 B 則……」的公式化對稱。** AI 生成辯證時極度迷戀這種「平衡報導」句型，但真人寫的討論語氣更主觀、更直接，不會每次都工整地切出正反兩面。改法：有時直接從一個立場寫起，寫到底後再提出質疑；有時用「但這裡有個問題」帶出第二種看法，而不是每次都「觀點 A 認為……觀點 B 則從……來回應」。
- **消滅空洞的過渡與總結排比。** 「這三組經歷共同指向一個結構性衝突」「一條貫穿始終的線索浮現」「這意味著……的保護可能需要制度層面的支持」——這些句子聽起來有智慧，實際上是「廢話文學」的高級版，沒有提供任何新資訊，只是把前面講過的概念重新包裝成漂亮的排比。如果一句過渡句拿掉後段落照樣通順，就不要寫。
- **避開 AI 預設轉折詞。** 「進一步」「值得注意的是」「本質上」「就此而言」「從這個意義上來說」這些是 LLM 的寫作樣板轉折詞。改用更自然的連接方式，或直接省略——很多時候段落之間不需要轉折詞也能讀。
- **避免整篇翻譯腔的抽象名詞。** AI 翻譯英文管理學文獻時，傾向直譯出大量冷冰冰的抽象名詞（「能動性」「臨在感」「動態調整」「結構性張力」）。整篇都是這種詞會讀起來像翻譯論文，不像學生寫的報告。遇到這類詞時想一下：如果要用白話文跟同學解釋這個概念，會怎麼說？用那個說法。只有在 Case 原文的關鍵術語才保留學術用法。

### 多元觀點的語氣差異

在呈現不同觀點（觀點 A / 觀點 B / 觀點 C）時，每個觀點的語氣要有些微差異，但差異必須自然、不突兀。

做法：
- 不同觀點可以在「斷言程度」上有差異。有的觀點語氣較篤定，有的帶有保留或試探。例如一方直接說「應該優先處理 X」，另一方用「如果考慮到 Y 的風險，恐怕需要更謹慎」。
- 不同觀點可以在「切入方式」上有差異。有的從原則出發，有的從實務經驗推論，有的從反面案例質疑。切入方式不同，句子結構自然就不一樣。
- 不同觀點可以在「關注焦點」上有差異。有的重視效率，語氣較務實簡潔；有的重視公平或倫理，語氣較慎重。

禁止：
- 不要為了「製造差異感」而讓某個觀點突然變得口語化或情緒化——這在正式報告裡會非常突兀。
- 不要用「！」或誇張的修辭來區分觀點。
- 不要讓語氣差異大到像是不同人寫的報告拼貼在一起。

目標是讓讀者自然感受到「這些觀點背後的思考邏輯不同」，而不是「這幾段文字的風格不同」。

## Step 8 — 自我審稿

依 `references/quality_rubric.md` 自評。

對每個 Case 各自依 rubric 評分。如果下列任一項不合格，先重寫再輸出 PDF：

- 任一 Case 只是摘要，缺少爭點
- 不同觀點只是並列，沒有互相回應
- 結論沒有顯示思考過程
- 延伸議題與 Case 關聯薄弱
- 有無來源的數字 / 事實
- 捏造組員說法
- PDF 內文出現亂碼、截字、空白頁或標題孤行
- 「不是…而是」句型出現超過 2 次（全文計）
- 超過 8 處中文詞括號附英文（每個 Case 各自計）
- 多數段落靠冒號展開後半句
- 每個爭點的展開結構幾乎一模一樣
- 兩個 Case 的分析框架、用語或行文節奏過於雷同（各 Case 應有自己的論述風格）
- 「橫跨」「交織」出現超過 1 次
- 出現「觀點 A 認為……觀點 B 則……」的公式化對稱句型超過 1 次
- 出現空洞的過渡排比句（如「共同指向一個結構性衝突」「一條貫穿始終的線索浮現」）
- 「進一步」「值得注意的是」「本質上」「就此而言」等 AI 預設轉折詞出現超過 2 次（全文計）
- 整段都是翻譯腔的抽象名詞，缺乏白話文的呼吸感

## Step 9 — 產生 PDF

執行：

```bash
python .claude/skills/case-report/scripts/render_pdf.py output/case_report.md output/case_report.pdf
```

如果失敗，先閱讀錯誤訊息並修復環境或改用可用的 PDF 工具，不要只停在 Markdown。

最後確認：

- `output/case_report.md`
- `output/case_report.pdf`

都存在。
